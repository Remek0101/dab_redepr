# dab_redepr – Project Documentation

A Databricks **Declarative Automation Bundle** (DAB, formerly "Databricks Asset Bundle") that deploys a
Citi Bike medallion ETL (bronze → silver → gold) to three environments (dev / test / prod) in three
different Azure Databricks workspaces. The ETL is implemented three ways (notebook job, Python-script job,
Lakeflow/DLT pipeline) and shares a small reusable Python package that is shipped as a **wheel (.whl)**.

## 2. `databricks.yml` – the bundle entry point

This file is the root of the bundle. The CLI reads it, merges in every file matched by `include`, picks one
**target**, substitutes variables, then deploys.

### 2.1 Top-level sections

| Section | In this project | Purpose |
|---|---|---|
| `bundle` | `name: dab_redepr`, `uuid: …` | Identity of the bundle. The name is used in the workspace path (`.bundle/<name>/<target>`) and in dev-mode resource prefixes. The `uuid` is generated by `databricks bundle init` and uniquely identifies the bundle. |
| `include` | `resources/*.yml` | Splits the config across files. Everything under `resources/` is merged in, so `databricks.yml` stays small. |
| `artifacts` | `dab_redepr` (type `whl`) | Tells the CLI how to build the Python wheel (see §5). |
| `variables` | `catalog`, `dev_flag`, `cluster` | Parameters whose values differ per environment (§2.2). |
| `targets` | `dev`, `test`, `prod` | Environments: workspace host, mode, per-target variable values, permissions (§2.3). |

(The `resources:` section itself – jobs and pipeline – lives in the included files, see §4.)

### 2.2 Variables

Referenced anywhere in YAML as `${var.<name>}`.

| Variable | Type | Default | dev | test | prod | Used for |
|---|---|---|---|---|---|---|
| `catalog` | string | `citibike_dev` | `citibike_dev` | `citibike_test` | `citibike_prod` | Unity Catalog catalog every table/volume is read from / written to. Passed to notebooks, scripts and the DLT pipeline. |
| `cluster` | string | `ds3_v2_sn` | `ds3_v2_sn` | `d8s_v3_sn` | `d8s_v3_sn` | **Name of a job cluster key** used by silver & gold tasks. Small cluster in dev, bigger one in test/prod. |
| `dev_flag` | bool | `true` | `true` | `false` | `false` | Declared to flag dev mode. **Currently not referenced by any resource** – safe to use or remove. |
| `ds3_v2_sn` | `complex` | cluster spec | – | – | – | Defined in `resources/job_cluster.yml`. Single-node `Standard_D4s_v3` (4 cores / 16 GB). |
| `d8s_v3_sn` | `complex` | cluster spec | – | – | – | Defined in `resources/job_cluster.yml`. Single-node `Standard_D8s_v3` (8 cores / 32 GB). |

**Complex variables.** `type: complex` lets a variable hold a whole object (here, a full `new_cluster`
definition). The job then writes `new_cluster: ${var.ds3_v2_sn}` instead of repeating ~20 lines of
cluster config in each job. Cluster settings of note: runtime `15.4.x-scala2.12`, single-node profile
(`num_workers: 0`, `spark.master: local[*, 4]`), Azure spot with on-demand fallback
(`SPOT_WITH_FALLBACK_AZURE`, first node on-demand), `data_security_mode: DATA_SECURITY_MODE_AUTO`.

**Where values come from (precedence, high → low):** CLI `--var catalog=x` → env var `BUNDLE_VAR_catalog`
→ `targets.<t>.variables` → `variables.<name>.default`.

Other substitutions seen in the YAML (not variables you define):

* `${bundle.name}`, `${bundle.target}` – built-in bundle references (used in `root_path`).
* `{{job.id}}`, `{{job.run_id}}`, `{{task.run_id}}`, `{{job.start_time.iso_datetime}}` – **Databricks job
  parameter references**, resolved at *run time* (not by the bundle). They are passed into the tasks so the
  `metadata` column can record lineage (which job / run / task / when).

### 2.3 Targets and modes

A target = one environment. Each has its own workspace `host`, variable values and settings. Select with
`databricks bundle deploy -t dev|test|prod`; `default: true` on `dev` makes it the default.

| | `dev` | `test` | `prod` |
|---|---|---|---|
| `mode` | `development` | `production` | `production` |
| Workspace | `adb-7405617289997499…` | `adb-7405616311562225…` | `adb-7405604627029762…` |
| Deploy path | `/Workspace/Users/<you>/.bundle/dab_redepr/dev` (auto) | `/Workspace/Shared/.bundle/dab_redepr/test` (explicit `root_path`) | `/Workspace/Shared/.bundle/dab_redepr/prod` |
| `permissions` | – | `remigiusz.be@gmail.com` CAN_MANAGE | same |
| `presets` | `artifacts_dynamic_version: true` | – | – |

#### What `mode: development` does
* Prefixes deployed resource names with `[dev <your_user_name>]`, so personal copies never collide with
  anyone else's or with real jobs.
* Pauses schedules and triggers (nothing fires unexpectedly).
* Deploys under your user folder automatically (`/Workspace/Users/<you>/.bundle/...`).
* Marks resources as dev (e.g. tags), allows running against an interactive cluster (`--compute-id`), and
  makes pipelines `development: true` (faster restarts, no retries).
* Meant for fast iteration; many "safety" checks are relaxed.

#### What `mode: production` does
* Resource names are **not** prefixed; schedules/triggers stay as defined (active).
* Validates safely: you must not use `/Workspace/Users/<other>` as `root_path`; the deploy path should be
  a shared location (here `/Workspace/Shared/...`) – hence the explicit `root_path`.
* If Git info is configured, checks the deployed branch matches the one declared in `git:`.
* Requires that you set up `permissions` / `run_as` explicitly rather than relying on the deploying user
  alone. Here the owner gets `CAN_MANAGE`.
* Does not allow overriding cluster with `--compute-id`.

> Note: `test` and `prod` use the **same mode** (`production`). The difference between them is the workspace,
> catalog (`citibike_test` vs `citibike_prod`) and `root_path`. "Test" is just a production-style deployment
> into a separate workspace.

#### `presets: artifacts_dynamic_version: true` (dev only)
Every deploy appends a unique timestamp to the wheel version. Without it, re-deploying a code change under
the *same* version `0.0.1` would make a cluster keep using its cached old wheel. With it, each build looks like
a new version and gets re-installed.

## 3. The three implementations of the ETL

All read CSVs from a landing Unity Catalog volume and build a medallion architecture:

```
/Volumes/<catalog>/00_landing/source_file   (CSV)
        │
        ▼  bronze: raw data + typed schema + `metadata` map
<catalog>.01_bronze.*
        │
        ▼  silver: + trip_duration_mins, + start date
<catalog>.02_silver.*
        │
        ▼  gold: per-day max/min/avg duration + trip count
<catalog>.03_gold.*
```

| | Notebook job | Script job | DLT pipeline |
|---|---|---|---|
| Resource file | `citybike_etl_notebook.yml` | `citybike_etl_script.yml` | `citibike_etl_dlt.yml` |
| Code | `citibike_etl/notebooks/*.ipynb` | `citibike_etl/scripts/*.py` | `citibike_etl/dlt/*.ipynb` |
| Task type | `notebook_task` | `spark_python_task` | pipeline `libraries: - notebook` |
| Gets params via | `base_parameters` → `dbutils.widgets.get(...)` | `parameters` list → `sys.argv[1..5]` (**positional!**) | `configuration: catalog` → `spark.conf.get("catalog")` |
| Compute | job clusters | job clusters | serverless + Photon |
| Output tables | `01_bronze.citibike`, `02_silver.citibike`, `03_gold.citibike` | `01_bronze.jc_citibike`, `02_silver.jc_citibike`, `03_gold.daily_ride_summary` | `bronze_jc_citibike_dlt`, `silver_jc_citibike_dlt`, `gold_daily_ride_summary_dlt` (in `schema: default`) |
| Task ordering | `depends_on` | `depends_on` | inferred from `dlt.read(...)` |

### 3.1 Job anatomy (`resources/citybike_etl_*.yml`)

```yaml
resources:
  jobs:
    citibike_etl_notebook:            # resource key (used by `bundle run citibike_etl_notebook`)
      name: citibike_etl_notebook     # display name in the workspace (prefixed in dev mode)
      tasks:
        - task_key: 01_bronze_citibike
          notebook_task: {notebook_path: ../citibike_etl/notebooks/01_bronze_citibike.ipynb, base_parameters: {...}}
          job_cluster_key: ds3_v2_sn  # bronze always on the small cluster
        - task_key: 02_silver_citibike
          depends_on: [{task_key: 01_bronze_citibike}]
          job_cluster_key: ${var.cluster}          # small in dev, big in test/prod
          libraries: [{whl: ../dist/*.whl}]        # install the wheel on this cluster
        - task_key: 03_gold_citibike
          depends_on: [{task_key: 02_silver_citibike}]
          job_cluster_key: ${var.cluster}
      job_clusters:                   # define the cluster keys referenced above
        - {job_cluster_key: ds3_v2_sn, new_cluster: ${var.ds3_v2_sn}}
        - {job_cluster_key: d8s_v3_sn, new_cluster: ${var.d8s_v3_sn}}
      queue: {enabled: true}          # queue runs instead of skipping if one is already running
```

Points worth knowing:

* Paths are **relative to the YAML file** (`../citibike_etl/...` because the file is in `resources/`).
* `${var.cluster}` is resolved to a *key name* (`ds3_v2_sn` or `d8s_v3_sn`), which must match a
  `job_cluster_key` in `job_clusters`. Both clusters are always declared; only the one referenced by a task
  is actually spun up. Bronze is hard-coded to `ds3_v2_sn` in every target.
* `base_parameters` become notebook **widgets**; the `catalog` parameter shows how a bundle variable flows
  down to code: `databricks.yml` target → `${var.catalog}` → widget → `f"{catalog}.01_bronze.citibike"`.
* Only the **silver** task has `libraries: whl:` because only silver imports `utils.citibike_utils`.
  Job-cluster libraries are per-task.
* The `metadata` map column (pipeline_id, run_id, task_id, processed timestamp) is built from those job
  parameters in bronze and silver, giving row-level lineage.

### 3.2 DLT pipeline (`resources/citibike_etl_dlt.yml`)

* `libraries` lists the three notebooks; Databricks builds a DAG from `@dlt.table` functions and
  `dlt.read(...)` calls, so no explicit ordering.
* `catalog: "${var.catalog}"` is the pipeline's target catalog; `configuration.catalog` additionally exposes it
  to code via `spark.conf.get("catalog")` (used for the volume path).
* `serverless: true`, `photon: true`, `schema: default`.
* The DLT silver/gold logic is written inline (it does *not* import the wheel), and uses the column name
  `trip_start_date` rather than `start_date`.

## 4. Shared code and the wheel

### 4.1 What goes in the wheel

`src/utils/citibike_utils.py` holds reusable PySpark functions:

* `get_trip_duration_mins(spark, df, start_col, end_col, output_col)` – adds `(end - start) / 60`.
* `timestamp_to_date(df, timestamp_col, output_col)` – adds `to_date(timestamp)`.

Silver notebook/script import it with `from utils.citibike_utils import ...`. Because it's installed as a
package, there is **no `src.` prefix** in the import. (Tests, which run from the repo, *do* use
`from src.utils.citibike_utils import ...` because there the package is not installed.)

### 4.2 How the wheel is built (the configuration chain)

1. **`setup.py`** (and `pyproject.toml`) defines the package: name `dab_redepr`, version `0.0.1`, and
   ```python
   packages=find_packages(where="src"), package_dir={"": "src"}
   ```
   i.e. "the packages live under `src/`, and the *package root is `src` itself*". That's why the wheel contains
   a top-level `utils/` package, not `src/utils/`:
   ```
   utils/__init__.py
   utils/citibike_utils.py
   dab_redepr-0.0.1.dist-info/{METADATA,WHEEL,top_level.txt,RECORD}
   ```
   `src/utils/__init__.py` is required so `find_packages` recognises `utils` as a package.
2. **`databricks.yml` → `artifacts`**:
   ```yaml
   artifacts:
     dab_redepr:
       type: whl
       path: .
       build: python setup.py bdist_wheel
   ```
   On `databricks bundle deploy` the CLI runs the build command in `path`, producing
   `dist/dab_redepr-0.0.1-py3-none-any.whl` (+ the `build/` folder).
3. **Upload & rewrite**: the CLI uploads the wheel into the bundle's `.internal/` artifacts folder in the
   workspace and rewrites `whl: ../dist/*.whl` in the job to that workspace path.
4. **Install at runtime**: the silver task's `libraries` entry makes Databricks pip-install the wheel on the
   job cluster before the task starts, so `import utils.citibike_utils` works.

`dist/` and `build/` are in `.gitignore` – the wheel is a build artifact and is regenerated on every deploy.

### 4.3 Manual / development flow (how it was originally created)

Before wiring this into the bundle the sequence was effectively:
1. Put the functions in `src/utils/` and add `__init__.py`.
2. Write `setup.py` (package config).
3. `python setup.py bdist_wheel` → wheel in `dist/`.
4. Upload the wheel to Databricks and install it on a cluster (cluster *Libraries*; for jobs, *Dependent
   libraries* on the task) – this is what the comments in `02_silver_citibike.py` describe.
5. Replace the manual steps with the `artifacts` + `libraries: whl:` configuration above so the CLI does it
   all on every deploy.

Local dev: `uv sync --dev` installs the dev group (`pytest`, `ruff`, `databricks-dlt`,
`databricks-connect>=15.4,<15.5`, `ipykernel`). Ruff line length is 120.

## 5. Putting it all together – what `databricks bundle deploy -t <target>` does

```
 databricks.yml  ──┐
 resources/*.yml ──┴─►  merge  ─►  select target  ─►  substitute ${var.*}
                                                          │
 setup.py + src/  ──►  `python setup.py bdist_wheel`  ──► dist/*.whl
                                                          │
                                              upload to workspace:
                                              • notebooks / scripts / files (sync)
                                              • wheel (artifacts folder)
                                              • create/update jobs + pipeline via Terraform engine
```

1. CLI loads `databricks.yml`, merges every `resources/*.yml`.
2. Applies the target (host, mode, variables, presets, permissions).
3. Builds the wheel (artifacts).
4. Syncs local files to `root_path` in the workspace (state kept in `.databricks/bundle/<target>/`).
5. Creates or updates the two jobs and the pipeline; `mode` decides naming/pausing/permissions.

### Day-to-day commands

```bash
databricks bundle validate -t dev            # check config & see resolved values
databricks bundle deploy   -t dev            # build wheel + deploy (dev is default)
databricks bundle run citibike_etl_notebook -t dev    # run a job (by resource key)
databricks bundle run citibike_etl_script   -t dev
databricks bundle run pipeline_citibike_etl_pipeline -t dev
databricks bundle deploy   -t test           # shared test env
databricks bundle deploy   -t prod           # production
databricks bundle destroy  -t dev            # remove deployed resources
```

### Resulting environments

| Target | Job names in workspace | Catalog | Silver/Gold compute |
|---|---|---|---|
| dev | `[dev <user>] citibike_etl_notebook` etc., schedules paused | `citibike_dev` | D4s_v3 |
| test | `citibike_etl_notebook` etc. | `citibike_test` | D8s_v3 |
| prod | `citibike_etl_notebook` etc. | `citibike_prod` | D8s_v3 |

Prerequisite in every workspace/catalog: schemas `00_landing` (with volume `source_file` holding the CSVs),
`01_bronze`, `02_silver`, `03_gold`, and permission for the deploying identity to create tables there.

## 7. Issues spotted while documenting (worth fixing)

1. **Script job: table name mismatch.** `scripts/01_bronze_citibike.py` writes `01_bronze.jc_citibike`, but
   `scripts/02_silver_citibike.py` reads `01_bronze.citibike` (the table written by the *notebook* job).
   Silver script will either fail or silently read the notebook job's data. Change silver to read
   `01_bronze.jc_citibike`.
2. **Script job: argument order differs per task.** Bronze/silver take 5 positional args, gold takes only
   `catalog` as `sys.argv[1]`. Fine today, but fragile – consider `argparse` with named params.
3. **Metadata key naming inconsistent**: scripts use `processed_date`, notebooks use `processed_at`.
4. **Notebook gold** uses `count("*")` → `trip_count`; script/DLT gold use `count("ride_id")` → `total_trips`;
   output table names differ across the three variants (by design to avoid collisions, but the column
   names should probably align).
5. **`dev_flag`** is declared and set per target but never used.
6. **`resources/job_cluster.yml`** is referenced as `job_clusters.yml` in a `databricks.yml` comment.
7. **`requirements.txt`** is UTF-16 encoded (created via PowerShell redirect) – `pip` can't read it as-is;
   re-export as UTF-8 (`pip freeze | Out-File -Encoding utf8 requirements.txt`) if you still need it.
8. **Gold task in jobs has no `base_parameters` for metadata**, unlike bronze/silver – intentional (gold
   doesn't write metadata) but worth knowing.
9. The `.databricks/bundle/` state currently only shows a `prod` folder with a very early file list
   (deployed 2026‑10‑28); redeploy to refresh.
